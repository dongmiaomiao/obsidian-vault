# 敏捷方法

> 从 [[知识体系]] 抽出的敏捷/适应型开发方法专题，含与传统（预测型）的对比。传统项目管理内容见 [[知识体系]]；五种生命周期类型的完整对照也在 [[知识体系]]。

## 一、开发方法选型：什么时候用敏捷

两个维度：**需求** 和 **技术方案/解决方案**。

| 需求 | 方案 | 采用的模式 |
| --- | --- | --- |
| 确定 | 确定 | 预测型 |
| 不确定 | 确定 | 增量 |
| 确定 | 不确定 | 迭代 |
| 不确定 | 不确定 | 敏捷 |
| 极其不确定 | 极其不确定 | 观望模式 |

> 举例：网站设计简单、需求确定，但要兼容火狐、谷歌、360 等不同浏览器——技术方案不确定，不对就改，所以用**迭代**。

### 增量 vs 迭代

- 增量：增加产品的功能——先做一块，再做一块，逐步做全。
- 迭代：循环、反复改进。备考 PMP 的过程就是循环：每天「听课 → 看书 → 做题」，一章学完再循环到下一章。
- 增量迭代：重复地想办法增加产品功能，边做边循环。

### 迭代/增量 vs 适应型（敏捷）

- 迭代和增量是两种独立的开发手段：迭代强调「循环改进」，增量强调「逐步加功能」。
- 适应型（敏捷）本质是**迭代 + 增量的组合**——既循环改进、又逐步交付，并用**固定时间盒（冲刺，通常 ≤ 4 周）**高频交付。
- 区别不在单一维度，而在「是否同时结合迭代与增量、是否用短周期固定时间盒」：单独用迭代或增量，周期通常较长、节奏较缓；敏捷靠短周期快速获得反馈。
- 明确能一次搞定 → 预测型；需要稳扎稳打、定期推出新功能、周期较长 → 迭代/增量；需求方案都模糊、需快速响应 → 敏捷。

## 二、传统项目 vs 敏捷项目：区别与利弊

### 区别对比

| 维度 | 传统（预测型/瀑布） | 敏捷（适应型） |
| --- | --- | --- |
| 适用场景 | 需求明确、变化少、技术成熟 | 需求与方案不确定、变化多、需快速响应 |
| 计划方式 | 前期一次性详细规划，按计划执行 | 短迭代滚动规划，边做边调整 |
| 交付方式 | 末期一次性交付完整成果 | 每轮迭代交付可用增量，持续交付价值 |
| 需求载体 | 需求文件（重、全、细） | 用户故事卡片（轻量：角色+目标+动机） |
| 范围 | 范围基准固定，靠变更控制 | 范围随反馈演进，PO 排序待办事项 |
| 变更 | 走正式变更控制（CCB），变更代价高 | 欢迎变更，代价低，直接进产品待办事项 |
| 风险管理 | 前期识别、规划，靠风险登记册 | 小步试错、快速验证，风险早暴露 |
| 质量 | 完工后检查验收把关（QC） | 每轮迭代内置质量（DoD），质量不可协商 |
| 沟通 | 正式书面、计划驱动 | 面对面、透明、信息发射源 |
| 团队 | 角色分工明确、按计划执行 | 自组织、跨职能通才 |
| 干系人 | 里程碑节点参与 | 持续、高频参与反馈 |

### 各自利弊

**传统（预测型）**

- 优点：可控性强、交付结果可预测；范围、进度、成本前期可承诺；适合合规要求高、成果不可逆的场景（如建筑、硬件制造）。
- 缺点：对变化响应慢；前期规划成本高；后期变更代价大；价值到末期才整体交付；需求一旦判断错，容易一错到底。

**敏捷（适应型）**

- 优点：快速响应变化；价值早期、持续交付；风险早暴露、试错成本低；客户持续参与、满意度高；拥抱不确定性。
- 缺点：不适合需求稳定、合规/监管严格、成果不可逆的场景；需要干系人高度投入；范围、成本、进度前期难以承诺；对团队成熟度和自组织要求高。

### 怎么选（逻辑）

1. 先看**需求**和**技术方案**是否确定 → 用「需求 × 方案」矩阵定位。
2. 再看**变更频率**：变化少、可预测 → 预测；变化多、需频繁反馈 → 敏捷。
3. 最后看**成果性质**：可逆、可拆分、软件类 → 适合敏捷；不可逆、一次性、实体类 → 适合预测。
4. 两者不冲突，可组合成**混合型**：整体预测、局部敏捷。

## 三、Scrum 三角色

标准 Scrum 有三个角色，希望有成熟、自组织的团队，项目经理采用放任型领导力风格，服务型权力下放给团队，由团队完成工作的规划、执行、控制：

1. **PO（产品负责人）**：负责产品的规划和设计；创建维护产品待办事项（大需求池）、优先级排序、需求价值评估。
   - PO 对所有的变更有决策权，只要涉及产品待办事项的增加删除都找 PO。
   - **PO 是一个人，不是一个委员会**；PO 需要有经验、有丰富的专业知识，组织必须尊重 PO 的决定。
2. **Scrum Master（敏捷教练/团队促进者）**：指导、辅导、启发、排除障碍、创造环境；帮团队营造环境、扫清障碍。某些情况下项目经理可以兼职 SM。
3. **开发团队（交付团队）**：把需求转化为成果（技术工作：开发、测试），成员跨职能、通才，配合 PO 分析评估需求规模/复杂度/工作量。

- PM 权力下放给 PO 和开发团队，变成服务型领导（治病救人）：能不干活就不干活，能不参与就不参与。
- PM 关注合作，确保团队有应对变更的能力。
- **PM 权力可以交接，责任不能被转移。**
- DoD（完成的定义）由 Scrum 团队共同约定；每个用户故事都应有 DoD 标准，完成并达到 DoD 才通过验收。

## 四、敏捷流程（一轮迭代）

产品待办事项（大需求池，所有要做的事都在）→ 迭代规划会（把下一轮要做的事搬到迭代待办事项）→ 迭代待办事项（小需求池）分解成任务 → 领取任务干活产出成果（符合 DoD = 完成增量）→ 迭代评审会（演示成果、获得客户反馈）→ 反馈放回产品待办事项 → 估算规模、风险价值排序 → 下一轮迭代，不断循环。

- 迭代规划会看三个数：**why**（冲刺目标）、**what**（冲刺范围）、**how**（冲刺任务）。
- 不论反馈有无新需求、新想法都放产品待办事项，避免下次迭代在错误道路上越走越远（不是一次做完，做一点看一点）。
- 所有反馈意见、改进事项、新需求、新想法，乃至风险应对措施、问题解决方案、纠正措施、预防措施、缺陷补救，都是未完项，放产品待办事项。

## 五、四大会议与站会

| 会议 | 看什么 |
| --- | --- |
| 迭代规划会 | 参与规划，这次迭代做什么 |
| 迭代评审会 | 参与验收，**看成果**（演示产品、获得反馈） |
| 回顾会 | 参与改进，**看过程**（做得好/不好，总结改进） |
| 每日站会 | 持续了解情况，让问题尽早暴露 |

> 迭代回顾会：总结这轮迭代做得好/不好的地方，给出改进建议措施，放回产品待办事项。
> 敏捷对标：收集需求、定义范围、创建 WBS 之后，工作完成产出的成果叫确认范围，对标敏捷叫迭代评审。
> 迭代评审会关注互动和反馈——反馈是为了防止在错误的道路上越走越远；评审会上不要只是演示，还要让人家来反馈。

### 站会与跨时区

- **每日站会**：让成员了解项目情况（所有成员轮流主持），让问题尽早暴露。
- **跨时区站会**：没法找到合适时间所有人参加，就分别召开各自站会，用击鼓传花的方式传递信息——美国人 9 点开站会，信息同步到中国；中国早上开站会，再把信息传给法国；法国开完传给美国。

## 六、需求排序与估算工具

- **MoSCoW 方法**：必须有、应该有、可以有、不能有——排优先级。
- **卡诺模型**：基本需求、期望需求、意外需求、无差异需求——分组排序。
- **扑克估算**：估算工作量和故事点。
- **理想人天**：理想情况下这活需要多少天。
- **T 恤尺码估算**：估算工作量。
- **产品待办事项细化会**（精化会/梳理会/研讨会）：分析故事是否明确、准备好没有，确定价值和规模，排定优先级，持续细化。

## 七、故事点

不同团队选取的典型故事不一样，估算结果也不一样，所以**故事点无法跨团队比较**。质量第一，缺陷越少越好，质量不可协商。敏捷要以团队绩效为标准，不求快只求稳。

## 八、看板与 WIP

- **看板**：让任务的流动可视化，产出成果、获得反馈。
- **WIP（在制品限制）**：拉动式进度计划，完成一个拉走一个。在复杂、高度变化、创新、不确定的环境下，干得多干得快不一定是好事——可能干得越多错得越多，要用**最小的成本、最小的代价去试错**。范围越小 → 周期越短 → 成本越低 → 试错代价越小。

## 九、敏捷中的进度与成本

- 尽可能不要延长迭代周期（时间盒固定、不能改），可在规划时分析迭代周期。
- 当前迭代落后进度计划：能完成的完成，实在完不成下次再说。
- 项目变更密集，可考虑缩短迭代长度，利于保持相对稳定工作。
- 敏捷追求稳定团队（加班影响绩效士气、加资源团队震荡）不提倡；关注专注，确保效率和质量。
- 成本：敏捷因不可预测，没必要花精力算成本（轻量级估算）。

## 十、敏捷中的范围

- **史诗**：超大需求，需细化、分解。
- **特征**：一堆需求。
- **故事**：一个需求，分解到合适的颗粒度。

## 十一、敏捷中的质量

- 质量不可协商，一定是可用的东西、有价值，客户才能体验（否则无法反馈）。
- 频繁开展质量与审核步骤（关注小批量工作），越早发现代价越低。
- 迭代产出质量不高、缺陷增多 → 需频繁检查。

## 十二、敏捷中的沟通

- **透明沟通**：产品待办事项、迭代待办事项、看板、燃尽图、燃起图、问题停车场——所有东西构成信息发射源，低科技高触感，一面墙。
- **拉动式沟通**：大家想了解项目情况就自己过来看，一目了然。
- 透明是为了更好地检视，检视是为了更好地适应。
- 团队分散世界各地时，考虑沟通的语言差异。

## 十三、其他敏捷实践

- **停车场**（临时挂起区）：把偏离主题的议题暂时挂起，保持会议不被打断。
- **西瓜项目**（时效性）：及时跟踪进展（外表绿、里面红）。
- **技术债务**：为短期效应选择易于实现的方案，长远带来消极影响；快速响应需求的非最优临时方案，需重构。
- 合作永远是最好的选项；以最小代价去试错；抓大放小。
- 外部障碍 → 团队促进者要积极主动；内部问题 → 鼓励大家自己解决。
- 外部来的变更不一定去分析原因，内部的问题一定要找原因（对症下药）。
- 私下的沟通：了解进度缓慢原因，分析并解决问题，再解决团队凝聚和士气问题。
