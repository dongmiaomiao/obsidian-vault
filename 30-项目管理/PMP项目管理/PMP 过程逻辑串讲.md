# PMP 过程逻辑串讲

> 把质量、范围、进度、资源、变更五个领域串成一条逻辑线，重点记「过程之间的先后与依赖」。细节可对照 [[PMP 知识整合]]。

## 一、质量管理：管过程 + 控结果

### 三个过程的定位

| 过程 | 关注 | 手段 | 能否减少缺陷 |
| --- | --- | --- | --- |
| 规划质量管理 | 定规矩 | 分析政策、标准、指标 → 决定怎么做质保/质控 | 重预防（源头） |
| 管理质量（质保 QA） | 过程 | 审计、过程改进 | 能——减少缺陷的发生 |
| 控制质量（质控 QC） | 结果 | 检查、测试 | 不能——只能发现、修复（亡羊补牢） |

**核心逻辑：**

1. 好的质量是**规划、设计**出来的，不是检查出来的 → **规划质量管理**先行，重预防。政策、标准、规范决定了质量活动怎么开展，所以要提前做好规划。
2. **管理质量**关注过程是否合规：过程符合政策、标准、程序、流程规范，结果通常不容易出问题，可以减少缺陷的出现和发生。
3. **控制质量**关注结果：对成果做检查、做测试，发现缺陷、修复缺陷。它是亡羊补牢，无法减少缺陷的发生——所以才需要有管理质量这个前置过程。

> 一句话区分：**管理质量 = 过程合规（做审计）；控制质量 = 结果合格（做检查）**。

### 可交付成果的流转（质量 → 范围）

```
指导与管理项目工作（按计划完成工作）
  → 可交付成果
  → 控制质量（团队自己先检查、测试，通过后）
  → 核实的可交付成果
  → 确认范围（客户、发起人正式验收）
  → 验收的可交付成果
  → 结束项目或阶段（变成最终产品/服务/成果的移交）
```

**好的做法：站好最后一班岗。** 团队自己对成果做检查、做测试，看是否能验收，别把半成品直接丢给客户——否则一旦客户发现缺陷，满意度下降，产生外部失败成本。所以流程是「**先控制质量，再确认范围**」。

## 二、范围管理：做且只做

项目范围管理关注「做且只做」：完成范围内的工作，并且**仅**完成范围内的工作。

### 流程

1. **收集需求**：拿到干系人登记册，想尽各种各样办法收集需求。
   - 亲和图：分组归类
   - 名义小组技术：排序
   - 需求表述不清 → 观察（看用户实际怎么干）
   - 需求不确定 → 原型（先做个原型给用户看）
   - 输出：**需求文件**。
   - 同时确保每个需求**有效、有价值**：是否用户真正需要，是否与章程、商业论证、需求评估、总体目标一致。

2. **定义范围**：根据需求，约定要创造什么样的产品/服务/成果，产出**范围说明书**——包括产品范围、项目范围、可交付成果、验收标准，以及**除外责任**（什么东西不包含在范围内）→ 代表大家达成共识。

3. **创建 WBS**：范围说明书虽然达成共识，但不好估算所需资源、时间、成本，也不好分工、不好管理控制，所以把大工作分解成小工作、小成果，分解到合适大小（比如 A 归王五、B 归张三、工作包归老李——各自对号入座）。
   - **WBS 词典**：详细解释每个工作包/控制账户的范围、进度、成本、质量、资源、沟通、风险、采购等各方面要求。

4. **范围基准 = 范围说明书 + WBS + WBS 词典**（找有权利的项目相关方审批）。

5. **确认范围**：验收（由客户、发起人正式验收）。

6. **控制范围**：绩效 + 变更。拿范围绩效数据与基准比较，看是否有偏差（该干的都干了、不该干的没干），有偏差 → 变更请求 → 交项目经理开展实施整体变更控制。

## 三、进度管理：从活动到进度基准

核心目标：项目能不能**按时**完成。

### 流程

1. **定义活动**：找到 WBS 最底层的工作包，分析完成它需要开展什么工作，就得到了「how」（活动）→ 得到活动列表。
2. **排列活动顺序**：关注先干啥、后干啥，排排序。
   - 用**紧前关系绘图法（PDM）**画成网络图。
   - 再分析逻辑关系/依赖关系：
     - **强制性 vs 选择性**：强制性由法律、合同或工作性质决定，顺序固定；选择性是团队基于最佳实践或偏好选的（选择的 = 可选的），存在优化空间。
     - **内部 vs 外部**：内部是项目活动之间的依赖（团队可控）；外部是项目活动与项目外工作之间的依赖（如等第三方交付）。
     - 分析这些依赖是串行还是并行。
3. **估算活动资源**（前置条件）：考虑资源可用性（资源日历）——3 个新手 + 1 个老手，工期不一样；实在没资源可考虑外包。
4. **估算活动持续时间**：根据资源需求来估算每个活动要多久。
5. **制定进度计划**：做出全部「作战计划」，谁在什么时间干什么事。进度计划一旦敲定，所有具体的开始/结束日期构成**进度基准**；把这些大事小情——项目、控制账户、工作包、活动都列出来。
6. **控制进度**：绩效 + 变更。进度数据与基准比较 → 进度绩效信息交给项目经理写报告；涉及进度的变更以变更请求的形式交项目经理开展实施整体变更控制。

> 延伸——进度压缩（赶工、快速跟进）的前提，是先找到**关键路径**。

## 四、资源管理：人、物、权责

### 规划资源管理（如何管理人和物）

1. **画组织架构图（组织分解结构 OBS）**：让员工知道自己属于哪个小团队、上下级关系、各自职责定位。
2. **定责任分配矩阵（RAM，如 RACI）**：把工作包、控制账户、活动等所有事情列出来，约定各自分工。
   - R：执行（谁落实）
   - A：负责/决策（谁做主，对结果承担最终责任）
   - C：咨询（征求谁的意见）
   - I：知会（结果、过程通知到谁）
   - 目的：防止「三个和尚没水喝」——1 个和尚要对自己负责，不挑水，没水喝；2 个和尚公平，一起挑水喝，公平合理、权责对等；3 个和尚权责一旦失衡，很容易崩溃。责任分配矩阵最主要的就是把大家的权、责、利说清楚，所有事情明确各自的职责。**每件事必须有一个 A**：平时民主，谈不拢时由 A 拍板，防止工作卡住。
   - 反过来用：通过 RACI 就能知道什么事和我有关、我去干什么事、什么事我说了算、什么事要征求谁的意见、什么事要通知到谁——把所有和我有关的事摘出来，就知道我未来要干什么。
3. **写文档（文本型）**：详细描述每个角色、每个岗位的职责和权限。

以上三者 → 写进**资源管理计划** + 制定**团队章程**：

- **资源管理计划**：团队成员的配备、培训、团建、辞退、表彰、惩罚等游戏规则。
- **团队章程**：由团队制定效果最佳；约定行为规范、基本准则（什么可接受/不可接受），划清边界，不要一言堂，尽早认可并遵守明确规则，有助于减少误解，规矩定得越早越好。

### 估算活动资源

- 输入：活动清单、资源日历（识别每种资源什么时间可用/不可用，考虑资源可用性）。
- 方法：
  - 类比估算：参考历史信息直接给结果
  - 自下而上估算：没把握时再细分
  - 参数估算：参考历史参数、变量经过计算给结果
- 输出：
  1. 资源需求（资源类型、数量、水平/等级）
  2. 估算依据（告诉老板为什么这么估，体现干活以数据、事实说话）
  3. 资源分解结构（方便我们统计分析，方便我们获取资源，方便我们去采购）

### 获取资源

- 前提：① 进度计划（什么时间干什么事）；② 资源需求（需要什么资源）。拿到的人叫**工作安排**（PMBOK 术语：团队派工单）；拿到的物叫**物资分配**（PMBOK 术语：物质资源分配）。
- 谈判渠道（优先级从高到低）：
  1. 职能经理：提供（最优）资源
  2. 其他项目经理：竞争稀缺资源（稀缺的东西会被抢）——项目间冲突的主要来源之一，找两个项目看能否协调（安排好、协调好，不要影响）
  3. 供应商：实在没资源再考虑
- 替代资源：能不用就不用，除非没得选。
- **预分派**：提前商定/约定的资源，对资源选定形成约束。

### 三联动

估算活动资源、估算活动持续时间、估算活动成本三个过程紧密关联、相互依赖——通盘考虑时间、资源数量/水平/等级、预算，才能制定出**可行**的进度计划。资源会牵一发而动全身，影响到时间、成本、质量，引发风险。

> 资源日历（每种资源的档期）→ 帮助估算资源（要考虑资源可用性，事业环境因素会限制工作）；项目日历（时间的可用性）→ 确定最终交付日期。

## 五、变更管理：实施整体变更控制

所有变更请求都要交给项目经理，任何人都可以提变更。流程：

```
变更请求 → 记录（变更日志）→ 综合分析评估（对进度、成本、质量、资源等的影响）
→ 决策（批准/否决）→ 更新 → 通知相关方
```

- 没有变更请求，不开展实施整体变更控制。
- 没人管的变更就是失控——失控的范围变化就是范围蔓延。
- 延伸——决策谁拍板：涉及基准（范围/进度/成本）的变更，交 **CCB（变更控制委员会）** 审查批准；不涉及基准的变更，项目经理有权直接批准。

## 六、一条主线串起来

- **质量 → 范围**：控制质量输出的「核实的可交付成果」是确认范围的输入；先质控，后验收。
- **范围 → 进度/成本**：范围基准是估算时间、成本的基础（WBS → 活动 → 资源 → 工期 → 成本）。
- **需求 → 价值**：每个需求要有价值、要关联到成果，最终交付有价值的产品/服务/成果（人家要啥咱给啥）→ 价值交付。
- **需求跟踪矩阵**：把需求关联到成果，跟踪每个成果的状态（完成测试、验收、移交），确保移交到用户手里的东西都做了质控、做了正式验收。
