# PMP 知识整合

> 由 [[PMP 项目管理]]、[[PMP 知识点速记]]、[[PMP 敏捷]]、[[PMP模考题笔记]]、[[PMP项目管理知识点]] 五份笔记整合而成；矛盾处已按 PMBOK 标准统一。

## 一、核心理念与项目定义

### 核心理念

- 事事皆项目，人人为项目。
- 管理学上没有绝对的对与错，永远是找**相对最合适**的选项。

### 什么是项目

项目是为创造独特的产品、服务或成果而进行的**临时性**工作。

- **产品**：手机、汽车、房子（新产品的研发，旧产品的改造升级）
- **服务**：通过工作达到的效果
- **成果**：比如科研成果、核酸检测

### 三大特性

**1. 独特性**

世界上没有两片相同的树叶。每个项目的成果都是独特的——可以是有形的（看得见摸得着），也可以是无形的（想法、创意、知识产权）。项目之间可能有重复的元素，但一定有不同：时间不同、位置不同、相关方不同、环境不同。不同就意味着不确定性，不确定性就是风险。

**2. 临时性**

项目有明确的开始时间和结束时间。目标实现了就结束，或者因其他原因异常终止，不能遥遥无期。

临时性不等于周期短——有的项目一两个月，有的十几年甚至几十年（比如三峡工程搞了 30 年）。但不管多长，必须有明确的时间边界。

另外，项目的临时性**不适用于**项目产出的产品、服务或成果。

> 异常终止：内部原因——公司战略转型、干越多赔越多、项目不会或不能达成目标；外部原因——法律法规变化、客户跑路、需求不存在了。不管是哪种，结束项目的决定必须得到有关当局的审批。

**3. 渐进明细性**

从高层级到底层级，从目标到范围到各种计划，整个过程随着工作推进不断细化、不断丰富。

> ⚠️ 渐进明细 ≠ 范围蔓延。范围蔓延是没经过控制的范围变化，是不好的。变更本身不可怕，可怕的是变更没人管——没有综合考虑对成本、进度、质量、沟通、采购的影响，草率做决策。关键在于**变更管理**。

## 二、项目 vs 运营

| 维度 | 项目 | 运营 |
| --- | --- | --- |
| 性质 | 临时性、独特性、渐进明晰性 | 持续性、重复性 |
| 目标 | 做完即结束 | 持续、重复开展 |
| 产出 | 独特的产品、服务、成果 | 相同品质的产品、服务、成果 |
| 过程 | 不适合标准化 | 尽量标准化、规范化 |

运营追求的是量产——持续地产出相同品质的产品、服务或成果。标准化、规范化是为了弥补人的不足，保证每次产出都一样。

**共性：**

- 都服务于公司战略，帮助战略计划落地。
- 都需要规划、执行和控制（管理工作相同）。
- 都需要资源/资金，并受其约束。

## 三、战略 → 项目组合 → 项目集 → 项目 → 运营

### 逻辑链条

1. 企业需要体现自己的**商业价值**（告诉投资人我们公司值多少钱）
2. 商业价值需要**战略计划**和管理
3. 战略计划通过**项目**和**运营**去落地
4. 项目和运营中，和公司战略匹配的，纳入**项目组合**管理
5. 项目是实现战略的一种手段 → 项目管理技能是企业实现战略的关键技能

> 华为重视 PMP，核心就是让员工掌握项目管理这种思维方式——从战略到战术层层转化，帮企业更好地实现各个层级的目标。

### 项目组合、项目集、项目

| 层次 | 关注点 | 回答的问题 |
| --- | --- | --- |
| 项目组合 | 事分轻重缓急，合理分配资源/资金（人、财、物），现阶段最重要的是什么、资源资金相应倾斜 | 做什么事是对的，优先级更高 |
| 项目集 | 多个相互关联（有依赖关系）的事情一次性处理好，关注最佳实践方法论 | 如何更好实现目标 |
| 项目 | 完成任务 | 如何把事情做好 |

- **项目组合**：一个大篮子，把跟公司战略匹配的事装进去，排序、分清优先级、合理分配人财物。篮子里的东西**不一定彼此依赖或直接相关**，可能包含项目集、项目、运营工作，太大可拆成子组合。
- **项目集**：多个事之间存在依赖关系（尤其成果上的依赖），放在一起管理，关注如何协调好、一次做到位。项目集里一定至少有一个项目。
- **项目**：关注如何把一件事做好、实现目标、完成任务。

简单说：

- 项目组合回答：**什么是对的？优先级怎么排？**（做正确的事）
- 项目集回答：**多个有依赖的事怎么一起搞定？**
- 项目回答：**单件事怎么做好？**（把事做正确）
- 运营回答：**怎么降本增效、持续产出？**

> 判断技巧：项目属于**项目集** → 跟其他事有依赖关系；项目属于**项目组合** → 跟公司战略有相关性。

## 四、生命周期与开发方法

### 生命周期类型

| 类型 | 特点 | 适用场景 |
| --- | --- | --- |
| 预测型（瀑布） | 充分了解产品，一次性交付 | 需求明确、能一次搞定 |
| 迭代型 | 循环交付、反复改进 | 技术方案不确定 |
| 增量型 | 逐步增加产品功能 | 范围（需求）不明确 |
| 适应型（敏捷） | 快速迭代，周期通常 2–4 周 | 目标不明确、需快速响应市场与反馈 |
| 混合型 | 根据项目情况，该预测的预测、该敏捷的敏捷；几个迭代并行推进 | 复杂场景 |

**增量 vs 迭代**

- 增量：增加产品的功能——先做一块，再做一块，逐步做全。
- 迭代：循环、反复改进。备考 PMP 的过程就是循环：每天「听课 → 看书 → 做题」，一章学完再循环到下一章。
- 增量迭代：重复地想办法增加产品功能，边做边循环。

**迭代型/增量型 vs 适应型**

- 两者本质一样：都是循环、都在增加功能。
- 区别在迭代周期长短：适应型 < 4 周；迭代和增量通常 > 4 周。
- 明确能一次搞定 → 预测型；需要稳扎稳打、定期推出新功能、迭代周期较长 → 迭代和增量。

### 需求 × 方案 → 选型

两个维度：**需求** 和 **技术方案/解决方案**。

| 需求 | 方案 | 采用的模式 |
| --- | --- | --- |
| 确定 | 确定 | 预测型 |
| 不确定 | 确定 | 增量 |
| 确定 | 不确定 | 迭代 |
| 不确定 | 不确定 | 敏捷 |
| 极其不确定 | 极其不确定 | 观望模式 |

> 举例：网站设计简单、需求确定，但要兼容火狐、谷歌、360 等不同浏览器——技术方案不确定，不对就改，所以用**迭代**。

### 项目生命周期 vs 项目管理生命周期

**项目生命周期**：根据项目特点，从启动到收尾经历的一系列阶段。不同类型项目阶段划分不同（取决于行业、企业特点），但共性是四阶段：**开始 → 组织与准备 → 执行项目工作 → 结束项目**。

两个特征：

- **变更代价**：早期低，后期高。越往后积累成本越多，变更代价越大。
- **风险**：由高到低。前期不确定性最大，随渐进明细而降低；但后期一旦出问题影响非常大 → 想办法让问题**前置暴露**，早发现早解决，变更成本也低。

**项目管理生命周期**：跟项目生命周期有相同的起点和终点，共存亡。阶段划分基于管理工作特点，即五大过程组。

### 产品生命周期

任何一款产品从 0 到 1、从生到死，六个共性阶段：**研发 → 引入市场 → 上升期 → 成熟期 → 衰退期 → 退出市场**。

- 刚需、高频、大市场的产品，成熟期长（如矿泉水——每天都要喝，到哪都有市场）。
- 疫情过后就不需要的产品，衰退期短（如核酸检测）。

产品生命周期里，每个阶段通常包含多个项目。

## 五、五大过程组与 PDCA

每个项目阶段都要重复开展五大过程组，包含十大知识领域、49 个管理过程。

1. **启动**：授权。授权项目经理开始项目或阶段 → 输出项目章程（有目标、有项目经理名字、写清楚有什么权利）
2. **规划**：制定行动方案 → 输出项目管理计划（怎么实现章程里的目标）
3. **执行**：按计划干活，产出可交付成果
4. **监控**：两件事——① 绩效（工作进展怎么样了）；② 变更（管好过程中的各种变化）
5. **收尾**：结束项目或阶段，总结、存档、移交

> 这五个过程组就是戴明环（PDCA）：Plan 计划 → Do 执行 → Check 监控 → Act 改进。
>
> **叫外卖的例子**：定好计划（吃什么）→ 打开平台点餐交钱（执行）→ 看外卖小哥到哪了、有没有取餐（监控）→ 发现上次优惠券没用、这次货比三家（改进）。一件事做完，接着下一个 PDCA，持续改进。

## 六、项目目标与制约因素

### 多快好省（项目目标）

- **多**（范围）：要做出什么样的产品/服务/成果，具备哪些功能。
- **快**（进度）：多长时间做完。
- **好**（质量）：达到什么样的标准和要求。
- **省**（成本）：花多少钱、在多少预算内完成。

中间是**范围**，旁边是约束性目标（时间、成本、质量），呈三角关系。

### 六大制约因素

**范围、进度、成本、质量、资源、风险**。任何一个因素变化，都会引起其他因素的连锁反应：

- 范围做多 → 需要更多时间 → 影响进度；
- 想缩短工期 → 增加资源 → 成本上升；
- 投入的资源水平参差 → 引发质量问题 → 又影响进度；
- 种种不确定性 → 带来风险。

所以要综合考虑，任何因素变化都要权衡它对其他因素的影响。

### 十大知识领域

从六大制约因素扩展，加上**沟通、采购、相关方**，再加**整合管理**，共同构成**十大知识领域**：整合、范围、进度、成本、质量、资源、沟通、风险、采购、相关方。

## 七、治理：权力的分配

要做的事明确了，接下来就需要人、需要定规矩。

- **组织治理**：定组织架构（几个部门、多少层级、各自职责）+ 定工作流程（请假、报销、采购等）+ 定制度、政策、程序、标准、规范 ≈ **权力的分配**。为组织指明政策、流程、程序、标准规范。
- **项目治理**：指导项目管理活动的框架、功能和过程 ≈ **项目上权力的分配**。

说白了就是：谁管什么事、谁有什么权限、大家怎么配合。

---

## 八、项目启动前三件事 + 阶段关口

在投入资源资金之前，先搞清三件事：

1. **需求评估**：搞清楚业务需要什么，找到商业机会（做什么项目、创造什么产品服务成果）。
2. **商业论证 + 效益管理计划**：分析怎么做、是否值得做，遵循两大原则：
   - 可行性（能不能做到）
   - 价值（能否赚到钱）
   - 没有可行性 → 不干；有可行性 + 有价值 → 可以干；有可行性但低价值/没价值 → 不干。
3. **项目启动**：有可行性、有价值，才投入资源资金开始干。

启动后也不是一劳永逸。两个阶段之间放一个**阶段关口**，验证项目是否还有可行性和价值，发现不行了及时止损。

项目结束后成果移交给运营，但项目结束时是否取得预期效益还不确定——这是效益管理计划要跟踪的事。

## 九、变更管理

计划之外的东西都叫变更。实施整体变更控制的流程：

1. 先有变更请求作为输入，没有变更请求不开展这个流程
2. 对变更做正式记录，记到变更日志里
3. 综合分析——范围、进度、成本、质量、资源、沟通、风险、采购，各知识领域该怎么调整，考虑周全后再做决策
4. **涉及基准的变更**：提交 CCB（变更控制委员会）审查和批准
5. **不涉及基准的变更**：项目经理有权利直接批准
6. 有了决策结果后，更新相关计划和文件，通知干系人落实执行

**关键点：**

- 所有的变更都要以变更请求的形式作为实施整体变更控制的输入。
- 项目经理要对实施整体变更控制承担最终责任。如果有人拿来一个已批准的变更，项目经理却不知道，说明没走流程。
- 变更太多就会失控，失去控制的变更就叫范围蔓延。
- 敏捷里的变更由 PO 管——只要涉及产品待办事项的增加删除都找 PO。PO 对所有的变更有决策权。

## 十、范围管理

- 创建 WBS：分解可以有效降低事务复杂程度，便于管理和控制。
- WBS 词典：用详细文档解释工期要求、质量标准、预算要求。
- **范围基准 = 范围说明书 + WBS + WBS 词典**

### 敏捷中的范围

- **史诗**：超大需求，需细化、分解。
- **特征**：一堆需求。
- **故事**：一个需求，分解到合适的颗粒度。

## 十一、进度管理

### 进度压缩

**赶工**和**快速跟进**。

- 赶工：串改并（通常导致成本上升，花钱越少越好）。
- 压缩的前提一定是关键路径。

### 看板与 WIP

- **看板**：让任务的流动可视化，产出成果、获得反馈。
- **WIP（在制品限制）**：拉动式进度计划，完成一个拉走一个。在复杂、高度变化、创新、不确定的环境下，干得多干得快不一定是好事——可能干得越多错得越多，要用**最小的成本、最小的代价去试错**。范围越小 → 周期越短 → 成本越低 → 试错代价越小。

### 敏捷进度要点

- 尽可能不要延长迭代周期（时间盒固定、不能改），可在规划时分析迭代周期。
- 当前迭代落后进度计划：能完成的完成，实在完不成下次再说。
- 项目变更密集，可考虑缩短迭代长度，利于保持相对稳定工作。
- 敏捷追求稳定团队（加班影响绩效士气、加资源团队震荡）不提倡；关注专注，确保效率和质量。

## 十二、成本管理

### 估算成本

根据资源、数量、水平等级（3 人 vs 5 人、新手 vs 老手成本不同）、进度计划（3 天 vs 5 天不同）等各种因素估算。

| 估算方法 | 特点 |
| --- | --- |
| 类比估算 | 直接出结果 |
| 参数估算 | 需要通过计算 |
| 自下而上估算 | 估算结果没把握 |
| 三点估算 | 有风险，结果不靠谱 |

> 敏捷因不可预测，没必要花精力算成本（轻量级估算）。

### 制定预算

汇总：活动 → 工作包 → 控制账户 → 整个项目。汇总成本 + 应急储备 → 成本基准。

### 直接成本 vs 间接成本

- **直接成本**：分摊不出去的，由项目组承担（如只用于专用地方的培训）。
- **间接成本**：公司出，然后收各项目的管理费，作为每个项目的间接成本（如其他项目也用得上的技能培训）。

## 十三、质量管理

### 质量成本

- 预防措施成本远低于检查或使用中发现并纠正错误的成本。
- 培训属预防成本，可减少失败成本。

### 质量与过程

项目的质量包括过程和结果，质量融入到过程和结果中。

> 厨师做饭，过程中不洗碗不洗手、过程不满足要求，但炒出来的菜好吃、客户满意——这种情况**不合格**：结果符合预期，但过程不符合要求。

### 管理质量三件事

1. **质量保证**：关注质量的合规性，就是审计，看实际过程是否符合程序、标准、规章制度。
2. **过程改进**：通过 PDCA、六西格玛等成熟质量体系持续改进优化。
3. **产品设计**：面向 X 的设计。

### 价值流

找到没价值、低价值的活动，看看能不能干掉，做到真正的降本增效。属于管理质量里的内容。

### 可交付成果 → QC → 核实的可交付成果 → 确认范围

指导与管理项目工作按计划完成工作，输出可交付成果。但别直接让客户验收——万一发现问题，会导致返工、客户满意度下降、外部失败成本。

稳妥做法：可交付成果先作为 QC（控制质量）的输入，由项目团队自己先检查、测试，看能否满足客户预期，没啥问题后输出**核实的可交付成果**，再走正式验收。

### 敏捷中的质量

- 质量不可协商，一定是可用的东西、有价值，客户才能体验（否则无法反馈）。
- 频繁开展质量与审核步骤（关注小批量工作），越早发现代价越低。
- 迭代产出质量不高、缺陷增多 → 需频繁检查。

## 十四、资源与团队管理

### 获取资源

根据进度计划、资源需求，把所需的人/物资拿到手。三个渠道优先级从高到低：

1. **找职能经理**：优先找职能经理，希望给优质资源。
2. **找其他项目经理**：抢竞争性的稀缺资源。
3. **找供应商**：实在不行再考虑采购。

### 建设团队 / 管理团队 / 控制资源

- **建设团队**：只管人，打造高绩效团队，搞团建建立信任、互相理解包容，成熟、自组织团队。
  - 作用：改进团队协作、增强人际关系、激励员工、减少摩擦、提升项目绩效。
- **管理团队**：关注人的问题（态度问题：不想学；能力问题：学不会），管理人与人之间的冲突。
- **控制资源**：跟踪物资使用情况，减少浪费。

**目的：** 确保项目经理和团队在正确的时间、地点使用正确的资源。

**集中办公 vs 虚拟团队：**

| 方式 | 优点 | 缺点 |
| --- | --- | --- |
| 集中办公 | 沟通效果好、凝聚力强、团队意识强 | 成本高、资源选择受限制 |
| 虚拟团队 | 成本低、资源选择多 | 团队意识差、沟通不方便 |

### 权责与技能

- 成员职责不清 → **RACI 矩阵**，确保每个工作包有明确责任人，确保全体团队清楚理解角色和职责。
- 有人技能不足 → 看**资源管理计划**怎么规定（培训？换人？辞退？调岗？）。资源管理计划包括如何招聘、遣散、配备、定义、培训、团建、奖励、辞退、惩罚。
- 人员缺失/离职 → 及时更新组织知识库，做好知识转移、工作交接有文档，避免知识流失。
- 冲突多次出现、问题升级 → 找更高层人员沟通。

### 塔克曼阶梯理论（团队发展模型）

1. **形成阶段**：目标明确 → 指挥，让大家各司其职。
2. **震荡阶段**：冲突多、矛盾多 → 教练，尽可能减少矛盾，学会协作。
3. **规范阶段**：互相理解 → 支持成员参与决策，培养团队决策能力，走向成熟。
4. **成熟阶段**：放任型领导、授权。
5. **解散阶段**。

- 项目经理应留意成员是否有意愿和能力完成工作，相应调整管理和领导力方式。
- 已展现能力和经验的成员 → 成熟就授权，不该管的别管。
- 技术能力较低的成员 → 强化监督，该管还是得管；新员工用权力发号施令。
- 不管是传统项目还是敏捷项目，思路一样，都是塔克曼阶梯。

## 十五、沟通管理

### 核心逻辑

沟通本质上就是传递信息：发文档、发资料、发邮件。重点是**规划沟通管理**，把沟通计划的方方面面都约定好，未来严格按计划执行。

两个代表性工具：

1. **沟通需求分析**
2. **沟通风格评估**——尽可能用对方喜欢的、偏好的沟通风格

沟通渠道随人员增加而不断增加，人多嘴杂。要简化沟通渠道，减少信息传递途径，防止信息越传越失真。

### 敏捷中的沟通

- **透明沟通**：产品待办事项、迭代待办事项、看板、燃尽图、燃起图、问题停车场——所有东西构成信息发射源，低科技高触感，一面墙。
- **拉动式沟通**：大家想了解项目情况就自己过来看，一目了然。
- 透明是为了更好地检视，检视是为了更好地适应。
- 团队分散世界各地时，考虑沟通的语言差异。

### 站会与跨时区

- **每日站会**：让成员了解项目情况（所有成员轮流主持），让问题尽早暴露。
- **跨时区站会**：没法找到合适时间所有人参加，就分别召开各自站会，用击鼓传花的方式传递信息——美国人 9 点开站会，信息同步到中国；中国早上开站会，再把信息传给法国；法国开完传给美国。

## 十六、风险管理

### 管理过程顺序

1. **规划风险管理**：制定概率和影响定义、概率和影响矩阵、RBS（风险分解结构）。
2. **识别风险**：发现啥记录啥，登记造册到风险登记册。
3. **定性风险分析**：分析概率和影响，查询矩阵确定风险优先级；再考虑紧迫性、临近性对优先级做调整，得到靠谱的排序结果。
4. **定量风险分析**：不一定所有项目都做，大规模项目才参考量化分析（按期完工概率、按预算完工概率、整体情况）。
5. **规划风险应对**：指定责任人，规划应对策略和措施。
6. **实施风险应对**：强调落实和执行，规划好的措施不落实等于白费，风险发生就成了问题。
7. **监督风险**：一个计（风险审计），一个查（风险审查）。
   - 风险审计：看风险管理过程什么地方做得好、不好，总结经验教训。
   - 风险审查：看应对措施管不管用，风险有没有变化。

### 常见考点

- 发现一个风险，先去翻风险登记册，确认有没有被识别过。
- 考风险管理过程的顺序。

### 风险应对策略

- **威胁（坏事）**：回避、转移、减轻、接受、上报。
- **机会（好事）**：开拓、分享、提高、接受、上报。

举例：

- **转移**：自己做饭不好吃，就叫外卖，花点钱把风险后果转给第三方。
- **回避**：手机提示升级操作系统，升级后有些 APP 不能用——那不升级了。
- **主动接受**：不兼容，出了问题再说，但提前准备了应急计划或应急储备。
- **被动接受**：啥都不准备，纯躺平。
- **上报**：超出权力范围的事就上报。

### 其他要点

- **根本原因分析**是识别风险的根据，分析风险产生的原因，跟场景没关系。
- **SWOT** 是分析优势带来的机会、劣势带来的坏事，也跟场景没关系。
- **头脑风暴**：集思广益、发散思维、畅所欲言，大家还会跟风。
- **德尔菲技术**：让大家匿名，防止因为对方的权力、身份、权威而不敢表达真实想法。
- 不可抗力一般属于小概率事件，通常不需开展风险管理，准备好灾难发生后的应急计划即可。
- **权变措施**：未知风险，纯意外，出现了意外再看怎么整。
- 高风险、技术、创新、技术不确定 → 去尝试、**刺探**。

## 十七、采购管理

### 合同类型取决于范围

| 范围情况 | 合同类型 |
| --- | --- |
| 范围明确 | 总价合同（范围很详细，可以一口价） |
| 范围不明确 | 成本补偿合同 |
| 范围不明确但需要快速获取资源 | 工料合同 |

- 甲方希望风险小 → 总价合同。
- **经济价格调整合同（EPA）**：适用于范围明确但周期长的情况——物价有波动、或用不同货币支付、汇率可能浮动，就加 EPA 条款。

### 采购三步走

1. **规划采购管理**：通过自制外购分析决定是否外部采购。如需采购，产出四样：招标文件、采购工作说明书、供方选择标准、独立成本估算。
2. **实施采购**：招标、投标、评标、中标、签约。
3. **控制采购**：跟踪合同执行情况，检查供应商工作和成果，该给钱的给钱，管理采购相关变更。看绩效、管变更，都属于控制采购。

### 选择题技巧

| 看到…… | 选…… |
| --- | --- |
| 甲方希望风险小 | 总价合同 |
| 没有范围 | 成本补偿合同（若还需快速获取资源 → 工料合同） |
| 完全消除风险 | 回避 |
| 想转移风险给第三方 | 转移 |
| 降低风险概率 | 减轻 |
| 不知道变更找谁 | 变更管理计划 |
| 卖方不清楚采购内容 | 投标人大会（公平、公正、澄清） |

## 十八、相关方管理

### 三板斧

**第一步：识别相关方**——不要只看字面意思，包括很多工作：

- 分析相关方的权力、作用、影响力、利益、兴趣爱好。
- 用方格、立方体、凸显模型、影响方向等工具对相关方分组，确定优先级——事分轻重缓急，人分三六九等。
- 相关方越早识别越好，尽量全部识别，尽量不要遗漏；出现新相关方 → 先更新登记册 → 相关方分析（分组、排序）；人员变化 → 更新相关方登记册。

**权力/利益方格：**

| 权力 | 利益 | 策略 |
| --- | --- | --- |
| 高 | 高 | 重点管理 |
| 高 | 低 | 令其满意 |
| 低 | 高 | 随时告知 |
| 低 | 低 | 监督 |

**第二步：规划相关方参与（看态度、定策略）**——先探明相关方的态度（反对？中立？不知情？），再看看期望他达到什么参与程度。比如张三目前反对，希望他能支持；李四目前只是口头支持，希望他有实际行动。

**第三步：规划沟通管理**——有了策略后再去规划沟通，**不要上来就沟通**。

> 把话说出去之前，咱是它的主人；话说出去之后，覆水难收，咱就变成奴隶了。一旦看到对方担忧、焦虑、不安、惶恐，要去理解，想办法走入他的内心世界。

### 态度问题 vs 沟通问题

- 李四说"我不听，我不愿意听你解释"——**态度问题，相关方管理做得不到位**。
- 李四说"我听不清楚"——**信息传递有问题，定位到沟通**。

### 关键原则

- 正面东西最大化，负面东西最小化。
- 不一定所有相关方都重点关注，但尽量不要遗漏。

## 十九、冲突管理

### 基本原则

冲突可能产生负面影响，也可能产生正面影响。只要能以建设性方式解决，坏事也能变好事。

面对冲突不能都不管，**该干预还得干预**，一切看情况：

- 太激烈了 → **缓**（缓解）
- 没条件解决 → **撤**（撤退/回避）
- 对方固执 → **妥协**
- 磨磨唧唧太犹豫 → **用权力**（强迫）
- 最好的方式 → **合作，面对问题解决问题**

### 各策略区分

| 策略 | 特点 |
| --- | --- |
| 撤退/回避 | 退出或推迟冲突，暂不解决；没条件时先撤，可留待他人/以后处理 |
| 妥协/调解 | 折中，双赢/双输；解决一部分，至少一定程度满意（心甘情愿地输也是妥协） |
| 强迫/命令 | 紧急情况下用权力给出决策结果（一方赢/一方输）。与回避的关键区别：回避没有给出决策结果，强迫是"你们都错了，就我对" |
| 合作/解决问题 | 双赢；了解冲突原因并提供解决方案 |
| 缓和/包容 | 对方态度不好（生气、着急、伤心、上火），先让对方别急别气，不处理，先让气氛冷静 |

冲突出现多次，考虑问题升级，找更高层级沟通。

### 与责任分配矩阵的关系

民主的缺点就是难以达成共识，一旦有分歧工作就推进不下去。所以在 RACI 责任分配矩阵里，**每个层级必须有一个 A**。一旦民主无法达成共识，需要这个 A 站出来独裁，防止工作卡住。

两个人有冲突导致事情进展不下去、三个和尚没水喝——都是责任分配失衡。

## 二十、敏捷专题

### Scrum 三角色

标准 Scrum 有三个角色，希望有成熟、自组织的团队，项目经理采用放任型领导力风格，服务型权力下放给团队，由团队完成工作的规划、执行、控制：

1. **PO（产品负责人）**：负责产品的规划和设计；创建维护产品待办事项（大需求池）、优先级排序、需求价值评估。
2. **Scrum Master（敏捷教练/团队促进者）**：指导、辅导、启发、排除障碍、创造环境；帮团队营造环境、扫清障碍。某些情况下项目经理可以兼职 SM。
3. **开发团队（交付团队）**：把需求转化为成果（技术工作：开发、测试），成员跨职能、通才，配合 PO 分析评估需求规模/复杂度/工作量。

- PM 权力下放给 PO 和开发团队，变成服务型领导（治病救人）：能不干活就不干活，能不参与就不参与。
- PM 关注合作，确保团队有应对变更的能力。
- **PM 权力可以交接，责任不能被转移。**
- DoD（完成的定义）由 Scrum 团队共同约定；每个用户故事都应有 DoD 标准，完成并达到 DoD 才通过验收。

### 敏捷流程（一轮迭代）

产品待办事项（大需求池，所有要做的事都在）→ 迭代规划会（把下一轮要做的事搬到迭代待办事项）→ 迭代待办事项（小需求池）分解成任务 → 领取任务干活产出成果（符合 DoD = 完成增量）→ 迭代评审会（演示成果、获得客户反馈）→ 反馈放回产品待办事项 → 估算规模、风险价值排序 → 下一轮迭代，不断循环。

- 迭代规划会看三个数：**why**（冲刺目标）、**what**（冲刺范围）、**how**（冲刺任务）。
- 不论反馈有无新需求、新想法都放产品待办事项，避免下次迭代在错误道路上越走越远（不是一次做完，做一点看一点）。
- 所有反馈意见、改进事项、新需求、新想法，乃至风险应对措施、问题解决方案、纠正措施、预防措施、缺陷补救，都是未完项，放产品待办事项。

### 四大会议

| 会议 | 看什么 |
| --- | --- |
| 迭代规划会 | 参与规划，这次迭代做什么 |
| 迭代评审会 | 参与验收，**看成果**（演示产品、获得反馈） |
| 回顾会 | 参与改进，**看过程**（做得好/不好，总结改进） |
| 每日站会 | 持续了解情况，让问题尽早暴露 |

> 迭代回顾会：总结这轮迭代做得好/不好的地方，给出改进建议措施，放回产品待办事项。
> 敏捷对标：收集需求、定义范围、创建 WBS 之后，工作完成产出的成果叫确认范围，对标敏捷叫迭代评审。

### 需求排序与估算工具

- **MoSCoW 方法**：必须有、应该有、可以有、不能有——排优先级。
- **卡诺模型**：基本需求、期望需求、意外需求、无差异需求——分组排序。
- **扑克估算**：估算工作量和故事点。
- **理想人天**：理想情况下这活需要多少天。
- **T 恤尺码估算**：估算工作量。
- **产品待办事项细化会**（精化会/梳理会/研讨会）：分析故事是否明确、准备好没有，确定价值和规模，排定优先级，持续细化。

### 故事点

不同团队选取的典型故事不一样，估算结果也不一样，所以**故事点无法跨团队比较**。质量第一，缺陷越少越好，质量不可协商。敏捷要以团队绩效为标准，不求快只求稳。

### 其他敏捷实践

- **停车场**（临时挂起区）：把偏离主题的议题暂时挂起，保持会议不被打断。
- **西瓜项目**（时效性）：及时跟踪进展（外表绿、里面红）。
- **技术债务**：为短期效应选择易于实现的方案，长远带来消极影响；快速响应需求的非最优临时方案，需重构。
- 合作永远是最好的选项；以最小代价去试错；抓大放小。
- 外部障碍 → 团队促进者要积极主动；内部问题 → 鼓励大家自己解决。
- 私下的沟通：了解进度缓慢原因，分析并解决问题，再解决团队凝聚和士气问题。

## 二十一、领导力与管理理论

### 领导力风格与权力

- 领导力就是让别人有主动性——以身作则。
- 领导力风格涉及权力，权力涉及责任分配矩阵。**民主和独裁想到权力。**
- 民主的缺点：很多时候无法达成共识、工作推不动 → 所以每个层级必须有一个 A，平时民主，该独裁时独裁。

### 各理论

- **光环效应**：业务能力出众不代表管理能力出众，技术好不代表管理能力强（考试考得好，不代表能当班长）。
- **奥齐理论（Z 理论）**：关注员工的成长、健康、家人、福利——"咱俩要过一辈子，你好我就好"。
- **麦格雷戈 X/Y 理论**：X 理论——人之初性本恶，大家懒惰，要严格管理；Y 理论——人之初性本善，管理较宽松。
- **马斯洛需求层次**：尊重大家各层次的需要。
- **弗鲁姆期望理论**：员工不傻，会分析事情的可行性和价值；发现没有可行性和价值，就不再抱有期望、失去动力。
- **赫兹伯格双因素理论**：
  - 保健因素：最重要的作用是**防止不满意**（如工资——不发工资、克扣工资，基本需求没保障才考虑跑路）。
  - 激励因素：最重要的作用是**促成满意**（成就、认同、责任、晋升——马斯洛的高层级需求）。
  - 激励因素没有时：既不是不满意也不是很满意，但肯定没动力（好死不死赖活着）；只有保健因素不具备时才会不满意。

## 二十二、可视化图表

- **燃尽图**：剩余工作量，直观展示迭代速度。
- **燃起图**：整个项目的总故事点数，展示迭代过程中范围的变化。
- **散点图**：判断两个变量是否存在联系。
- 燃尽图、燃起图用于实时测量，帮助团队了解工作能否按时完成。

## 二十三、优先级：艾森豪威尔矩阵

按两个属性判断：**重要程度** 和 **紧急程度**。

| | 紧急 | 不紧急 |
| --- | --- | --- |
| **重要** | 马上做 | 有规划地做 |
| **不重要** | 授权别人处理（事急，需马上响应） | 尽量忽略/不做 |

## 二十四、问题解决流程

定义问题 → 分析原因 → 制定方案 → 选择方案 → 执行方案 → 跟踪效果

- 出现问题先分析，了解情况后才能更好地评估影响。
- 遇到问题先分析原因，引导团队解决问题。
- 存在冲突，先了解冲突的来源和原因才能对症下药。
- 问题再次出现 → 要分析原因，防止治标不治本。

## 二十五、其他要点

### 先有章程后有计划

项目章程代表项目的正式启动，体现这个事合法合规，代表项目经理的正式授权，授权我们有权动用组织的资源。没有章程，这个事就不合法。

**章程谁爱写谁写，但一定要发起人签字、认可。**

制定项目章程的输入包括组织过程资产——比如产品有问题，先看历史记录、经验教训，之前项目产品有问题的原因是啥。

### 文化意识

不同国家和地区、民族、种族、宗教、信仰——鼓励成员具有文化意识，减少不必要的误解、冲突和矛盾。

### 总结经验教训

不管是采购审计、质量审计还是风险审计，都是回顾过程——什么地方做得好、做得不好，总结经验教训以便改进，目的是确保**未来项目不遇到同样的问题**。

### 项目管理办公室（PMO）

主要职责在于项目管理，更关注项目的方法、标准、规范、政策、流程的制定，让项目变得有序、有条不紊，工作重心是方法论。除此之外协调项目之间的资源、沟通、冲突（主要职责不是协调资源）。

### 混合型方法

几个开发迭代并行推进，敏捷加预测就叫混合；根据项目情况，该预测的预测、该敏捷的敏捷。

### 需求收集方法

- 需求不确定 → **原型法**（做出原型给用户看）。
- 需求表述不清 → **观察法**（观察用户实际工作，或工作跟随）。
- 技术不确定 → 用**迭代**解决。
- 范围不明确 → 用**增量**解决。
- **亲和图**：对需求/想法做分组归类。
- **名义小组技术**：对需求做排序。

> 用户体验不佳 → 早期让用户经常参与；演示过程中收到反馈 → 回顾中反思改进；团队协作是项目成功的关键因素。
